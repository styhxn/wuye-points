00 阅读指南

先弄清楚三件事，后面所有角色都不会读乱。

3 个前提
前提一 · 角色分两层 登录角色写在 residents.role 和 JWT 里，决定“你能进哪个端、走哪套鉴权”；叠加身份写在业务表里（楼长表、负责人表、组长表、店铺表），决定“你在住户身份之上还能做什么”。一个人可以同时是业主、楼长、业主小店店主、一级代理，role 仍然是 resident。这是本项目 2026-10 之后最重要的模型变化。
前提二 · 钱分三种 积分是物业体系里的消费返利，默认 100 分 = 1 元，只能花、不能提现；物业币是 1:1 元的体系内储值，可消费、可转物业，商家收到后可申请兑换现金；现金走微信支付。三者不能互相直接兑换，订单里可以用“积分 + 物业币 + 现金”混合支付。
前提三 · 代码现状优先 文档里凡是写“代码现状”的地方，都是指当前仓库真实行为，不代表产品最终目标。比如：社区管理员目前是空壳、活动组长不参与分账、商户退款没有商家审核入口。这些不是让你现在改，而是避免联调时按 PRD 预期去验收，最后对不上。
你会看到含义怎么用

02 住户主线

从微信登录到下单、缴费、社区互动，住户是整套系统的流量入口，也是所有身份的底座。

8 个阶段
01 住户 · 进入 微信登录、绑定物业、建立身份 没有独立注册页；首次进入就要确定“属于哪个物业公司” 展开
1微信登录小程序 code 调 /auth/wechat-login，后端换 openid；没有记录就建号：role=resident、userType=owner、active。
2确定物业首次登录必须带 propertyCompanyId；之后 JWT 固定该物业，所有数据范围都按它隔离。
3绑定手机号POST /auth/bind-phone。不绑也能登录，但商家、提现、找回等场景需要手机号匹配。
4选小区 / 房号住户可选小区和房间；楼栋、单元、房号只能物业改，住户只能提交变更申请等审批。
5完善资料姓名、头像、性别、年龄、婚姻、是否有子女；提交后按配置领取一次性奖励。
6“我的”页标签/auth/profile 返回 7 个 isXxx 标签，前端据此显示楼长、负责人、组长、小店、代理入口。

JWT 里有什么：sub=residentId，claims 包含 role、propertyCompanyId、familyId、tv（token 版本）。每次请求都会校验 tv 和住户状态，所以禁用、冻结、登出可以即时失效。

真实提醒 管理端和 C 端是同一张 residents 表。平台/物业账号也是 residents 里的一行，只是 role 不同，通过 /auth/admin-login 手机号 + BCrypt 密码登录。当前 app.auth.test-mode 默认 true，会放开历史口令 admin123456 并跳过“普通住户无管理端登录权限”校验——这是联调临时措施，上线前必须关闭。
资料奖励的坑 奖励按 社区 > 物业 > 统筹 > 平台 的 scope 优先级取配置，oncePerUser 默认 true。但 family_completed 条件依赖生日字段，而全仓库没有生日写入接口；其他普通字段也只校验“配置存在”，不校验是否真的填了。联调时不要把它当成严格的风控。
02 住户 · 家庭 家庭池：一个人开家，全家共用一个钱包 创建家庭会立刻把户主个人积分/物业币全部搬进家庭池 展开
1户主创建必须是非租户、当前无家庭、同物业；创建时填小区、楼栋、单元、房号。
2资产搬入户主个人积分和物业币全额转入家庭池，个人余额清零；之后新获得的积分仍进家庭池，新发放/充值的物业币进个人余额。
3成员加入只能户主操作；成员须已注册手机号、非租户、同物业；上限 15 人；加入即共享家庭池。
4消费顺序订单/物业费/服务单带 familyId 时，默认先用家庭池，不够再用个人池。
5退出 / 移除按“家庭余额 ÷ 家庭人数”平均分给退出者；户主不能退出。
6投票权意见箱投票按家庭计算，一户一票，不是一人一票。
真实提醒 家庭有 auditStatus 字段，创建时写 pending，但没有任何审核读取或审批接口，所以实际不阻塞。成员加入也没有审核。退出按人数均分，不看谁贡献得多——这是当前产品规则，不是计算错误。
03 住户 · 积分 积分：默认 100 分 = 1 元，只能花，不能提现 获取渠道比 PRD 少；签到/活动没有 C 端入口 展开

04 住户 · 物业币 物业币：1 币 = 1 元，可充值、可消费，住户不能直接提现 商家收到物业币后可以申请兑换现金，这是它和积分的最大区别 展开
1充值POST /property-coins/recharge 走微信预下单，回调按 PaymentRecord 幂等入账，1 元 = 1 币。
2订单返币仅当商家开启 coinRebateEnabled 且抽佣率 ≥ 20% 时，按 (物业币支付 + 现金支付) × coinRebateRate 返。
3消费商城（受物业商城规则约束）、物业费、服务/咨询；混合支付里物业币和积分可同时用。
4过期物业配置 coinExpiryDays 后过期；按最早流水逐笔核销，过期金额进物业积分池。
5转物业住户可主动把物业币转给物业，只扣家庭池（有家庭时）。
6商家兑现金商家用 /coin-withdrawals 申请，1:1 扣币，默认 0.6% 手续费，物业/平台审核。
真实提醒 ① 住户没有物业币提现入口，CoinWithdrawalController 只放行 merchant。② 冻结 coinFrozen 会拦截消费；已发起的充值回调仍会入账，但余额不可用。③ 物业币“使用条件”（最低消费、最大抵扣比例）当前只在前端展示，订单侧只校验商城开关和最大抵扣比例，没有逐条校验使用条件。
05 住户 · 物业费 物业费：账单由物业建，住户只负责查和缴 没有自动出账任务；准时缴清奖励 100 积分 展开
1物业建账单管理端 POST /admin/property-fees 创建；费用类型：物业/停车/水/电。
2住户查询GET /property-fees/my、GET /property-fees/{id}。
3选择支付property_coin / point / wechat / mixed；混合支付必须覆盖应付金额。
4现金到账含现金时先微信预下单，账单保持未缴；回调成功才落账。
5准时奖励结清且早于到期日，奖 100 积分 + 徽章，积分同步进家庭池。
6欠费与催缴状态 unpaid/partial/paid/overdue；催缴走 preview → send，站内信真实落库。
真实提醒 ① 物业费没有自动出账定时任务，账单必须由管理端创建。② 催缴的微信渠道只有统计，全部跳过，当前只有站内信。③ 物业费支付只更新 property_fees 并扣积分/币，不写物业公司结算账户；物业公司分成账户靠订单分账和平台调账，见 §11。
06 住户 · 商城 从下单到确认收货：一条订单的完整生命周期 支付方式、履约方式、退款入口都在这一节 展开

下单前

  • 只能看到 audit_status=approved、status=active 的商家；商品需 active 且有库存。
  • 商家的“服务社区”和“社区距离”目前只是展示配置，不参与下单校验；跨社区能不能下单，代码没有拦。
  • 会员价优先：商品有 memberDiscountPrice 时按会员价；否则按商品价。

下单

1提交订单POST /orders：商家、商品与数量、地址、联系电话、备注、familyId；初始 pending。
2服务端算价应付 = 商品金额 + 运费 − 优惠券；运费取商家配送费/满免门槛；服务端定价，不信前端。
3支付拆分纯积分/纯物业币即时扣；纯微信全额预下单；混合支付校验积分+物业币不超过应付。
4库存微信预下单即扣库存；30 分钟未支付自动关单并还库存；支付回调不再重复扣。
5返利支付成功后按规则返积分/物业币；优惠券核销；订单进入 paid。
6取消pending 取消会关微信单并还库存；已支付取消会退积分/币、退现金、冲返利、还库存。

支付后走哪条路

订单类型支付后状态后续谁推动

退款

paid / delivering→ refunding→ refunded/ refund_rejected
  • 住户发起，受开关 wechat-split.user-refund-enabled 控制，默认 false。
  • 审核只有物业/平台管理员，商家没有同意/拒绝退款的入口；商家只能拒团购核实。
  • 通过后：退积分/物业币、还库存、扣回返现、退现金、冲正业主结算；驳回后订单进入 refund_rejected，之后不能再取消。
联调最容易踩的顺序问题 退款开关默认关闭时，住户点退款会直接失败；开启后，退款审核也不在商家端，而在物业/平台后台。如果按“商家同意退款”去设计前端页面，会找不到接口。

发布后进入商家队列，5 分钟轮转；商家可接单、跳过、报价；住户确认报价并支付后生成 confirmed 服务工单。matching / negotiating 阶段可取消。

食堂

  • 食堂单支付后直接 completed，不配送。
  • 主商家可给食堂充值“定向余额”，订单页会展示可用余额。
  • 未通：CanteenService.consumeForOrder 没有任何调用点，定向余额目前只展示、不实际扣减。

快递

  • 住户没有寄件/收件下单入口；配送单全部来自商城订单履约。
  • 平台配送单进入抢单大厅；快递员抢单后 pending → accepted → delivering → completed。
  • 超时无人抢 → property_fallback，由物业兜底或再指派。
  • 配送费：商家配送费优先，满 freeDeliveryThreshold 免；平台配送基数 = 实付运费 + 满额补贴。

03 商家主线

商家不是独立账号体系，而是“住户账号 + 一行店铺”。理解这一点，后面所有“按手机号找店”的逻辑就顺了。

7 个阶段
01 商家 · 入驻 申请、审核、建店、建账号 审核通过只建店铺，不会自动建登录账号 展开
1提交申请POST /merchants：名称、类目、联系电话、地址、封面/视频、配送费、满免门槛、抽佣率、积分兑换比。
2生成待审店创建 PlatformMerchant + Merchant(pending_audit, normal, active) + 物业配置（默认抽佣 0.1、积分 100:1、返币关）。
3物业/平台审核仅 pending_audit 可审；通过 → approved + active，可同时改等级/类目/配送费；驳回 → rejected。
4建登录账号管理端 /admin/role-accounts 建 role=merchant 的 residents 行，并把店铺置为 approved/active。
5商家登录走 /auth/admin-login；后端按“手机号 + 当前物业”找最新店铺。
6微信进件（可选）/merchants/my/applyment 提交资料 → 微信审核 → 签约，为分账/收付通做准备。
真实提醒 ① 一个 merchant 只挂一个 property_company_id；同一平台商家要在多个物业经营，会为每个物业各建一行，费率独立。
② 商家等级只影响列表排序（official 100 / property 50 / normal 0），不改变费率或权限；只有 platform_admin 能改等级。
③ 商家被 frozen 后：商品、券、积分、广告、服务请求、提现全部不可用，买家下单被拒，商品对外不可见；但 /orders 仍可按手机号查历史订单。

03 商家 · 接单 订单进来后，商家要做什么 支付成功不等于订单完成；商家还要选履约、发货、处理核实 展开
1收到 paid 订单纯积分/币支付即时 paid；微信支付回调后 paid。
2选履约方式支付后 30 分钟内选 merchant_self（自配）或 courier_hall（平台配送）；超时默认平台配送。
3团购核实团购单需商家核实，pending_verification → verified；拒绝会取消并退款。
4发货/自配商家自配：merchant_self → merchant_delivering → completed，商家确认即订单完成。
5平台配送骑手接单后 delivering；骑手完成只推进配送单，订单等住户确认或超时自动完成。
6改派管理端可强改履约方式并留痕；已结束订单（completed/cancelled/refunded）不可改。

商家能看到的订单动作：确认发货、完成自配、核实团购、查看订单/销售统计；没有“同意退款”按钮，退款审核在物业/平台。

05 商家 · 售后 退款、拒单、服务请求 商家没有退款审核权；这是当前代码的硬边界 展开
  • 退款：住户申请 → 订单 refunding → 物业/平台审核 → refunded 或 refund_rejected。通过后退积分/币、还库存、扣回返现、退现金、冲正结算。商家端没有审核入口。
  • 团购拒单：商家核实拒绝会走 cancelAndRefund，订单取消并退款，取消方记为商家。
  • 已支付取消：由系统/管理端触发，退积分/币、退现金、冲返利、还库存。
  • 服务请求：商家在 5 分钟轮转里接单/跳过/报价；住户支付报价后生成服务工单。服务请求只扣住户积分/币，没有商家现金分账流水。
联调注意 如果前端按“商家同意退款”做页面，会找不到接口。退款审核只有 property_admin / platform_admin。另外 refund_rejected 后订单不能再取消，用户只能继续履约或走线下。
06 商家 · 结算 订单完成后，商家到底拿多少 抽佣基数、积分/币成本、四级分账，一次讲清 展开

订单进入 completed 时，系统写一条 distribution_records 快照，并按订单快照绑定楼长、经理、负责人。商家实得 = 商品实付 − 抽佣基数（再由平台盘分走）；积分/物业币成本先从抽佣基数里扣，扣成负数记 deficit，由物业池吸收。

商品订单分账（代码口径）
抽佣基数 = (订单总额 − 优惠券) × 商家 commissionRate
可分配   = 抽佣基数 − 积分成本(积分 ÷ 兑换比) − 物业币成本

一级三档（必须分完）：
  平台     = 可分配 × platformShareRate
  物业毛   = 可分配 × propertyShareRate
  管理盘   = 可分配 − 平台 − 物业毛

管理盘往下（有统筹时）：
  板块毛   = 管理盘 × sectorLeaderRate
  个体     = 板块毛 × individualLeaderRate
  板块     = 板块毛 − 个体
  统筹     = 管理盘 − 板块毛

物业内部：
  楼长毛   = 物业毛 × buildingLeaderRate（订单快照）
  经理     = 楼长毛 × managerRate
  楼长净额 = 楼长毛 − 经理

配送：
  基数     = 实付运费 + 满额补贴
  平台配送 = 基数 × platformDeliveryShareRate
  骑手     = 基数 − 平台配送
参数默认/生产值谁配置生效方式
商家抽佣率 commissionRate默认 0.10入驻时填，审核时可改下单/完成时读配置
积分兑换比 pointExchangeRate默认 100（100 分 = 1 元）商家物业配置下单/分账时读配置
平台 platformShareRate生产库默认 0平台完成时写分账快照
物业 propertyShareRate生产库默认 0.30平台完成时写分账快照
统筹 coordinatorShareRate生产库默认 0.70（管理盘余额）平台完成时写分账快照
板块 sectorLeaderRate默认 0.10（占管理盘）平台完成时写分账快照
个体 individualLeaderRate默认 0（占板块毛）平台完成时写分账快照
楼长比例任命时默认 0.10（占物业毛）物业/平台订单创建时写快照
经理比例默认 0（占楼长毛）物业/平台订单创建时写快照
平台配送分成 platformDeliveryShareRate按物业配置平台完成时计算
快照 vs 实时 分成比例在订单完成时写入 distribution_records，属于快照，之后改配置不影响已完成订单；结算开关、手续费率、商城抵扣上限、积分兑换比属于实时读。联调时改完比例要拿新订单验证。
07 商家 · 提现 可提现余额、审核、打款 商家、组长、技工走同一个提现接口；物业/负责人走另一个 展开
1算可提现已完成订单的商家分成收入 − 已占用（pending/approved/completed）− 已提现；单笔上限 999999.99。
2申请POST /merchant/withdrawals，费率取物业 withdrawalFeeRate，默认 0.6%。
3审核pending → approved → completed；拒绝回 rejected，不占额度。人工打款并写 transferProof。
4冻结withdrawalBlocked=true 时直接把可提现置 0，但仍可查历史。
5物业币兑换商家可把收到的物业币按 1:1 申请兑换现金，默认 0.6% 手续费，走 /coin-withdrawals。
6到账口径直连模式是内部台账 + 人工打款；普通分账/收付通模式下，微信侧已实时分账的部分会从可提现里扣掉，避免双算。
真实提醒 ① 纯 resident 的一级代理没有提现入口：MerchantSupport.requireCurrentWithdrawableMerchant 只放行 merchant / activity_leader / technician / 组长身份，DistributorController 也没有提现端点。② 技工提现走 /merchant/withdrawals，但收入来自服务单，不写 withdrawal_records。③ 平台收益只读，不能提现。
