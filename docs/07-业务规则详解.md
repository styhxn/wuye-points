## 1. 概览

### 1.1 业务规则总览

本系统围绕"物业-统筹-板块-个体"四级分成模型与"积分+物业币"双货币体系展开，所有业务在多物业公司数据隔离前提下运行。核心规则可归纳为：

| 规则域 | 核心约束 | 数据表锚点 |
|--------|----------|------------|
| 四级分成 | 物业 30% → 统筹 70%；板块从统筹抽 10%；个体从板块抽 | `distribution_records`、`coordinators`、`sector_leaders`、`individual_leaders` |
| 积分归属 | 按住户所属物业 T 归属，非商家所属物业 | `orders.property_company_id` |
| 双货币 | 积分与物业币独立运作，不可互兑 | `point_records`、`property_coin_records` |
| 积分池 | 三大入池来源，资金由物业承担 | `point_pools`、`point_pool_records` |
| 家庭制 | 上限 15 人，积分合并家庭池，一户一票 | `families`、`vote_records` |
| 平台商家库 | 基础信息一次录入，各物业独立挂接配置 | `platform_merchants`、`merchants`、`merchant_property_configs` |
| 物业币管控 | 可冻结/隐藏，过期清零入积分池 | `residents.coin_frozen`、`coin_expiry_records` |
| 2年清零 | 积分 2 年未使用 + 欠费 → 清零入池 | `property_fees`、`point_records` |
| 配送费 | 物业配置起步价，快递员每单固定报酬 | `delivery_rules`、`deliveries` |
| 邻居私聊 | 每日限制次数（默认 2 次） | `neighbor_contact_limits` |

### 1.2 术语表

| 术语 | 含义 | 关联字段/表 |
|------|------|-------------|
| 物业 T | 住户所属物业公司（住户当前归属） | `residents.property_company_id` |
| 抽佣比例 R_T | 商家在物业 T 下的抽佣比例 | `merchant_property_configs.commission_rate` |
| 积分兑换比 | 多少积分=1 元（如 200 积分=1 元） | `merchant_property_configs.point_exchange_rate` |
| 可分利润 | 消费金额 × 抽佣比例 − 积分成本 − 物业币成本 | `distribution_records.distributable_amount` |
| 统筹 | 物业公司下设的统筹角色，拿 70% | `coordinators` |
| 板块负责人 | 统筹下设的板块主管，从统筹中抽 10% | `sector_leaders` |
| 个体负责人 | 板块下设的具体个体，从板块中抽取 | `individual_leaders` |
| 积分池 | 兑换差额/过期/清零资金的沉淀池 | `point_pools` |
| 家庭池 | 家庭成员积分合并的累计余额 | `families.point_balance` |
| 物业币 | 仅在本物业内使用的虚拟货币 | `residents.coin_balance` |
| 抵扣比率 | 100 积分=1 元时为 0.01 | `property_companies.point_to_fee_rate` |

## 2. 四级分成机制

### 2.1 规则描述

每笔订单完成支付后，系统按四级模型对可分利润进行分配：

- 第一级：物业公司拿 30%（`property_share_rate`，默认 0.3000）
- 第二级：统筹拿 70%（`coordinator_share_rate`，默认 0.7000）
- 第三级：板块负责人从统筹的 70% 中抽取 10%（`sector_leader_rate`，默认 0.1000）
- 第四级：个体负责人从板块负责人抽得的部分中再抽取（`individual_leader_rate`，默认 0.0000）

> 注意：板块负责人抽的是统筹的份额，不是总的可分利润；个体负责人抽的是板块负责人的份额，不是统筹份额。

### 2.2 完整公式

设：
- `P` = 订单消费金额（`orders.total_amount`）
- `R_T` = 商家在物业 T 的抽佣比例（`merchant_property_configs.commission_rate`）
- `ExR` = 积分兑换比（`merchant_property_configs.point_exchange_rate`，单位：积分/元）
- `PtUsed` = 混合支付使用的积分（`orders.point_used`）
- `CnUsed` = 混合支付使用的物业币（`orders.coin_used`）
- `PC` = 物业公司分成比例（`property_companies.property_share_rate`）
- `CC` = 统筹分成比例（`property_companies.coordinator_share_rate`）
- `SL` = 板块负责人比例（`property_companies.sector_leader_rate`）
- `IL` = 个体负责人比例（`property_companies.individual_leader_rate`）

**步骤 1：计算积分成本**

```
point_cost = PtUsed / ExR
```

> 即用户用积分抵扣的部分，按商家设定的兑换比换算成商家成本。

**步骤 2：计算物业币成本**

```
coin_cost = CnUsed
```

> 物业币 1:1 抵扣现金，故其成本即使用金额。

**步骤 3：计算可分利润**

```
distributable_amount = P × R_T − point_cost − coin_cost
```

**步骤 4：四级分成**

```
property_share  = distributable_amount × PC                       // 物业 30%
coordinator_raw = distributable_amount × CC                       // 统筹 70%（未扣除板块）
sector_leader_share = coordinator_raw × SL                        // 板块从统筹抽 10%
individual_leader_share = sector_leader_share × IL                // 个体从板块抽
coordinator_share = coordinator_raw − sector_leader_share         // 统筹实际所得
```

### 2.3 计算示例

#### 示例 A：纯积分消费

- 消费金额 `P` = 0 元（纯积分兑换商品）
- 商家抽佣 `R_T` = 0.20
- 兑换比 `ExR` = 200（200 积分=1 元）
- 使用积分 `PtUsed` = 1000，`CnUsed` = 0

```
point_cost      = 1000 / 200 = 5.00 元
coin_cost       = 0.00
distributable_amount = 0 × 0.20 − 5.00 − 0 = −5.00 元（负值，见 2.5 边界处理）
```

> 纯积分兑换场景下可分利润为负，按 2.5 规则处理：所有分成记为 0，差额由商家自行承担或入积分池（视物业配置）。

#### 示例 B：纯物业币消费

- 消费金额 `P` = 100 元（用户支付 100 物业币）
- 商家抽佣 `R_T` = 0.15
- `PtUsed` = 0，`CnUsed` = 100

```
point_cost      = 0.00
coin_cost       = 100.00
distributable_amount = 100 × 0.15 − 0 − 100 = −85.00 元
```

> 物业币 1:1 抵扣现金，但抽佣基数仅按 P×R_T 计算；当 CnUsed 占比过高时可分利润为负，按边界规则处理。

#### 示例 C：混合支付（典型场景）

- 消费金额 `P` = 200 元
- 用户：现金 100 元 + 物业币 50 元 + 积分 10000（兑换比 200）
- 商家抽佣 `R_T` = 0.10
- PC=0.30，CC=0.70，SL=0.10，IL=0.00

```
point_cost      = 10000 / 200 = 50.00 元
coin_cost       = 50.00 元
distributable_amount = 200 × 0.10 − 50.00 − 50.00 = 20.00 − 100.00 = −80.00 元
```

> 此处因积分成本过高导致负值，实际生产中需校验积分兑换比合理性。建议在配置层校验 `R_T × P ≥ point_cost + coin_cost`。

#### 示例 D：正向可分利润案例

- 消费金额 `P` = 500 元（纯微信支付）
- `R_T` = 0.10
- `PtUsed` = 0，`CnUsed` = 0
- PC=0.30，CC=0.70，SL=0.10，IL=0.05

```
point_cost      = 0.00
coin_cost       = 0.00
distributable_amount = 500 × 0.10 − 0 − 0 = 50.00 元

property_share  = 50 × 0.30 = 15.00 元
coordinator_raw = 50 × 0.70 = 35.00 元
sector_leader_share = 35 × 0.10 = 3.50 元
individual_leader_share = 3.50 × 0.05 = 0.175 元
coordinator_share = 35 − 3.50 = 31.50 元
```

最终各方可分金额：物业 15.00 / 统筹 31.50 / 板块 3.325 / 个体 0.175。

### 2.4 负责人定位规则

订单完成后，系统需定位三级负责人，依据为订单的 `property_company_id`（住户所属物业 T）。

```java
// 伪代码：定位三级负责人
public DistributionContext locateLeaders(Order order) {
    String propertyId = order.getPropertyCompanyId();   // 住户所属物业 T
    Long merchantId = order.getMerchantId();

    // 1. 定位统筹：物业 T 下唯一在职统筹
    Coordinator coordinator = coordinatorRepository
        .findFirstByPropertyCompanyIdAndStatus(propertyId, "active");
    // 一个物业通常仅配置 1 个统筹；若多个则取主统筹（commission_rate 最大者）

    // 2. 定位板块负责人：按商家所属板块匹配
    //    板块字段：elderly/medical/education/cleaning/canteen/pet/life_service
    String sector = merchantSectorResolver.resolve(merchantId, propertyId);
    SectorLeader sectorLeader = sectorLeaderRepository
        .findFirstByPropertyCompanyIdAndSectorAndCoordinatorIdAndStatus(
            propertyId, sector, coordinator.getId(), "active");

    // 3. 定位个体负责人：按商家+板块匹配
    IndividualLeader individualLeader = individualLeaderRepository
        .findFirstBySectorLeaderIdAndSectorAndStatus(
            sectorLeader.getId(), sector, "active");

    return new DistributionContext(coordinator, sectorLeader, individualLeader);
}
```

字段映射：
- `distribution_records.coordinator_id` ← `coordinators.id`
- `distribution_records.sector_leader_id` ← `sector_leaders.id`
- `distribution_records.individual_leader_id` ← `individual_leaders.id`

### 2.5 边界情况处理

| 边界场景 | 处理策略 |
|----------|----------|
| 统筹不存在 | `coordinator_share`、`sector_leader_share`、`individual_leader_share` 全置 0；全部可分利润归物业（即 `property_share = distributable_amount`） |
| 板块负责人不存在 | `sector_leader_share = 0`，`individual_leader_share = 0`；统筹全额保留 70% |
| 个体负责人不存在 | `individual_leader_share = 0`；板块负责人保留其全部抽得份额 |
| 比例为 0（如 `IL=0`） | `individual_leader_share = 0`，相应份额不上移，归属上一级 |
| 可分利润为负 | 所有分成字段置 0；负值差额入积分池（`point_pool_records.source='pool_diff'`），由物业公司承担；同时在 `distribution_records` 中保留 `distributable_amount` 负值以便审计 |
| 订单退款 | 反向冲销：在 `distribution_records` 创建负数红冲记录，按原分成比例回滚各方余额 |
| 商家未配置 `merchant_property_configs` | 拒绝下单，提示"商家在该物业下未完成挂接配置" |

### 2.6 数据表字段映射

| 字段 | 表 | 含义 |
|------|----|------|
| `total_amount` | `orders` | 消费金额 P |
| `commission_rate` | `merchant_property_configs` | 抽佣比例 R_T |
| `point_exchange_rate` | `merchant_property_configs` | 积分兑换比 ExR |
| `point_used` | `orders` | 混合支付积分 |
| `coin_used` | `orders` | 混合支付物业币 |
| `point_cost` | `distribution_records` | 积分成本 |
| `coin_cost` | `distribution_records` | 物业币成本 |
| `distributable_amount` | `distribution_records` | 可分利润 |
| `property_share` | `distribution_records` | 物业分成 |
| `coordinator_share` | `distribution_records` | 统筹实际所得 |
| `sector_leader_share` | `distribution_records` | 板块负责人所得 |
| `individual_leader_share` | `distribution_records` | 个体负责人所得 |

## 3. 积分归属规则

### 3.1 规则描述

积分归属的核心规则：**按住户所属物业 T 计算，而非商家所属物业**。即使用户在跨物业挂接的商家消费，积分也归入户的当前物业。

### 3.2 住户所属物业 T 的判定逻辑

```java
// 伪代码：判定住户所属物业 T
public String resolvePropertyT(String residentId) {
    Resident r = residentRepository.findById(residentId);
    // 主判定字段：residents.property_company_id
    if (r.getPropertyCompanyId() == null) {
        throw new BizException("住户未绑定物业公司，无法归属积分");
    }
    // 校验状态
    if (!"active".equals(r.getStatus())) {
        throw new BizException("住户状态异常，无法归属积分");
    }
    return r.getPropertyCompanyId();
}
```

判定优先级：
1. `residents.property_company_id`（主字段，必填）
2. 通过 `residents.community_id` → `communities.property_company_id` 间接确认（一致性校验）
3. 用户跨物业迁移时，新归属物业 T 自迁移生效日起计算新积分；历史积分保留在原物业

### 3.3 商家跨物业挂接场景

商家通过 `merchants` 表挂接到多个物业，每个挂接在 `merchant_property_configs` 中独立配置抽佣比例等参数：

```
平台商家 platform_merchants (id=pm_001, name="好邻居超市")
    ├── merchants (id=mch_001, property_company_id=pc_A, ...)  ← 物业 A 挂接
    │     └── merchant_property_configs (commission_rate=0.10, point_exchange_rate=200)
    └── merchants (id=mch_002, property_company_id=pc_B, ...)  ← 物业 B 挂接
          └── merchant_property_configs (commission_rate=0.15, point_exchange_rate=150)
```

场景：物业 A 的住户 R 在物业 B 挂接的商家 mch_002 下单：
- 订单 `orders.property_company_id` = R 的所属物业 = pc_A（**非** pc_B）
- 抽佣比例取 `merchant_property_configs` 中 `(merchant_id=mch_002, property_company_id=pc_A)` 的记录
- 若 mch_002 未在 pc_A 下挂接配置，则拒绝下单（见 2.5）

> 关键：抽佣配置按"住户物业 T + 商家"匹配，而非"商家挂接物业"匹配。这要求商家在所有目标住户物业下都有挂接配置。

### 3.4 与分成的关系

| 字段 | 归属依据 |
|------|----------|
| `orders.property_company_id` | 住户物业 T |
| `distribution_records.property_company_id` | 同订单，即住户物业 T |
| `distribution_records.commission_rate` | 取 `merchant_property_configs` 中 `(merchant_id, property_company_id=住户T)` 的记录 |
| 积分入账（`point_records`） | `property_company_id` = 住户物业 T |
| 物业币入账（`property_coin_records`） | `property_company_id` = 住户物业 T |

### 3.5 异常处理

- 住户 `property_company_id` 为空：拒绝消费，提示"请联系物业完善归属信息"
- 住户物业与小区物业不一致：以 `residents.property_company_id` 为准，记录告警日志
- 商家在住户物业 T 下未挂接：拒绝下单，错误码 `MERCHANT_NOT_LINKED_TO_PROPERTY`

## 4. 双货币体系

### 4.1 规则描述

系统采用"积分 + 物业币"双货币体系，二者独立运作，**不可互兑**：
- 积分：通过消费、活动、签到等获取，可抵扣物业费、兑换商品
- 物业币：通过物业发放、商家返现等获取，可消费抵扣，可冻结/隐藏

### 4.2 积分规则

#### 4.2.1 获取（earn）

| 来源 | `point_records.source` | 说明 |
|------|------------------------|------|
| 消费返积分 | `order` | 按商家配置的兑换比反向计算 |
| 活动 | `activity` | 活动奖励 |
| 签到 | `sign_in` | 每日签到 |
| 手动调整 | `manual` | 物业人工调整 |
| 商家录入 | `merchant_grant` | 商家将购买积分录入给住户 |

#### 4.2.2 消费（spend）

- 积分兑换商品：扣减 `residents.point_balance`（或 `families.point_balance`）
- 积分抵扣物业费：100 积分 = 1 元（由 `property_companies.point_to_fee_rate=0.01` 配置）
- 混合支付：积分 + 物业币 + 现金，记入 `orders.point_used`

#### 4.2.3 转移（transfer）

仅限家庭内成员间转移，转移后合并到家庭池 `families.point_balance`。跨家庭转移禁止。

#### 4.2.4 过期（expire）

- 默认 730 天（2 年）过期，由 `point_rules.expire_days` 配置
- 过期积分不入积分池，直接销账（与"2 年欠费清零入池"区分）

#### 4.2.5 入池（pool_in）

仅在以下情况入池（详见第 5 章）：
- 兑换比例差额
- 2 年欠费清零

### 4.3 物业币规则

#### 4.3.1 发放（earn）

- 自动发放：`property_companies.coin_issue_mode='auto'`
- 人工审核：`property_companies.coin_issue_mode='manual_approval'`
- 商家返现：`merchant_property_configs.coin_rebate_enabled=true` 且 `commission_rate ≥ 0.20` 时生效

#### 4.3.2 冻结/解冻

```java
// 伪代码：冻结物业币
public void freezeCoin(String residentId, String operatorId, String reason) {
    Resident r = residentRepository.findById(residentId);
    if (r.isCoinFrozen()) {
        throw new BizException("物业币已处于冻结状态");
    }
    r.setCoinFrozen(true);
    residentRepository.save(r);

    coinFreezeRecordsRepository.save(CoinFreezeRecord.builder()
        .residentId(residentId)
        .propertyCompanyId(r.getPropertyCompanyId())
        .action("freeze")
        .amount(r.getCoinBalance())
        .reason(reason)
        .operatorId(operatorId)
        .build());
}
```

- 冻结后 `residents.coin_frozen=true`，禁止消费、提现、转移
- 解冻为反向操作，记 `action='unfreeze'`
- 默认冻结：`property_companies.coin_freeze_default=true` 时新用户默认冻结

#### 4.3.3 隐藏

`residents.coin_hidden=true` 时前端不显示物业币卡片，但余额保留。受 `property_companies.coin_display_enabled` 全局开关控制。

#### 4.3.4 过期

- 有效期由 `property_companies.coin_expiry_days`（默认 365 天）配置
- 过期清零金额入积分池（详见第 5 章）
- 记入 `coin_expiry_records` 表

#### 4.3.5 兑换

仅商家可将物业币兑换现金（住户不可），通过 `coin_withdrawals` 表申请，需审核。

### 4.4 不可互兑的强制约束

系统在多个层面强制积分与物业币不可互兑：

```java
// 伪代码：禁止互兑校验
public void validateNoExchange(PointRecord pt, CoinRecord cn) {
    if (pt.getSource() == Source.POINT_TO_COIN
        || cn.getSource() == Source.COIN_TO_POINT) {
        throw new BizException("积分与物业币不可互兑");
    }
}
```

- 接口层：不提供"积分转物业币""物业币转积分"接口
- 数据层：`point_records.source` 与 `property_coin_records.source` 枚举中均无互兑类型
- 审计层：定时任务扫描异常互兑记录，触发告警

### 4.5 100积分=1元 抵扣规则

```
抵扣金额（元） = 积分数量 × point_to_fee_rate
              = 100 × 0.01 = 1.00 元
```

- `property_companies.point_to_fee_rate` 默认 0.0100（100 积分=1 元）
- 各物业可独立配置此比率
- 抵扣仅作用于物业费（`property_fees`），不适用于商品消费
- 抵扣后扣减 `property_fees.point_deducted`，并记 `point_records.source='fee_deduct'`

|------|----|------|
| `point_balance` | `residents`、`families` | 积分余额 |
| `coin_balance` | `residents`、`families` | 物业币余额 |
| `coin_frozen` | `residents` | 物业币冻结标志 |
| `coin_hidden` | `residents` | 物业币隐藏标志 |
| `point_to_fee_rate` | `property_companies` | 积分抵扣比率 |
| `coin_expiry_days` | `property_companies` | 物业币有效期 |

## 5. 积分池机制

### 5.1 规则描述

积分池是物业公司维度的资金沉淀池，资金**由物业公司承担**。每个物业公司在 `point_pools` 表中有且仅有一条记录（`uk_property_company` 唯一索引）。

### 5.2 三大入池来源

#### 来源 1：兑换比例差额（exchange_diff）

当商家设定的积分兑换比 `point_exchange_rate` 与系统标准比率不一致时，差额入池。

```
标准兑换比 StdExR = 1 / point_to_fee_rate = 1 / 0.01 = 100 积分/元
商家兑换比 ExR = 200 积分/元（即 200 积分=1 元，对商家更优惠）

用户用 PtUsed 积分兑换：
    商家成本 point_cost = PtUsed / ExR = PtUsed / 200
    标准价值 std_value  = PtUsed / StdExR = PtUsed / 100
    差额 diff = std_value − point_cost
              = PtUsed × (1/100 − 1/200)
              = PtUsed × 0.005

差额 diff 入池，由物业承担。
```

#### 来源 2：物业币过期清零（coin_expired）

物业币过期清零金额按 1:1 入池：

```
pool_in_amount = expired_amount（物业币清零金额）
```

记入 `coin_expiry_records.pool_in_amount`，同时写 `point_pool_records.source='coin_expired'`。

#### 来源 3：2年欠费清零（fee_clear）

详见第 8 章。住户积分 2 年未使用且欠费，清零金额按 `point_to_fee_rate` 换算后入池：

```
pool_in_amount = cleared_points × point_to_fee_rate
```

### 5.3 出池规则

积分池资金可用于：
- 弥补分成计算中的负差额（`source='pool_diff'`，对应 `point_pool_records.pool_type='pool_out'`）
- 物业公司主动调出用于运营活动（需审计日志）
- 不允许直接提现给个人

```java
// 伪代码：入池操作
public void poolIn(String propertyId, BigDecimal amount, String source, String sourceId) {
    PointPool pool = pointPoolRepository.findByPropertyCompanyId(propertyId);
    BigDecimal before = pool.getBalance();
    pool.setBalance(before.add(amount));
    pool.setTotalIn(pool.getTotalIn().add(amount));
    pointPoolRepository.save(pool);

    pointPoolRecordsRepository.save(PointPoolRecord.builder()
        .propertyCompanyId(propertyId)
        .poolType("pool_in")
        .amount(amount)
        .balance(pool.getBalance())
        .source(source)           // exchange_diff / coin_expired / fee_clear
        .sourceId(sourceId)
        .build());
}
```

### 5.4 资金承担方

- **物业公司**承担积分池资金缺口
- 积分池余额为负时，表示物业已垫付资金，需在财务报表中体现
- 不允许跨物业调拨积分池资金

### 5.5 记录表结构说明

`point_pool_records` 字段：

| 字段 | 含义 |
|------|------|
| `pool_type` | `pool_in` 入池 / `pool_out` 出池 |
| `amount` | 金额（正数） |
| `balance` | 操作后池余额 |
| `source` | `exchange_diff` / `coin_expired` / `fee_clear` / `spend` / `pool_diff` |
| `source_id` | 关联业务记录 ID |

## 6. 家庭制规则

### 6.1 规则描述

家庭是积分合并与投票的基本单位：
- 上限 15 人
- 积分合并到家庭池 `families.point_balance`
- 一户一票（`families.vote_weight=1`）

### 6.2 创建/加入/退出家庭流程

#### 6.2.1 创建家庭

```java
// 伪代码：创建家庭
public Family createFamily(String ownerId, String propertyId, FamilyForm form) {
    Resident owner = residentRepository.findById(ownerId);
    if (owner.getFamilyId() != null) {
        throw new BizException("已属于某家庭，需先退出");
    }
    Family family = Family.builder()
        .id(IdGenerator.next("fam"))
        .ownerId(ownerId)
        .propertyCompanyId(propertyId)
        .name(form.getName())
        .memberCount(1)
        .pointBalance(owner.getPointBalance())
        .coinBalance(owner.getCoinBalance())
        .voteWeight(1)
        .auditStatus("pending")    // 需物业审核
        .status("active")
        .build();
    family = familyRepository.save(family);

    owner.setFamilyId(family.getId());
    residentRepository.save(owner);
    return family;
}
```

#### 6.2.2 加入家庭

```java
public void joinFamily(String residentId, String familyId) {
    Family family = familyRepository.findById(familyId);
    // 15 人上限校验
    if (family.getMemberCount() >= 15) {
        throw new BizException("家庭人数已达上限 15 人");
    }
    Resident r = residentRepository.findById(residentId);
    if (r.getFamilyId() != null) {
        throw new BizException("已属于其他家庭");
    }
    // 跨物业校验
    if (!r.getPropertyCompanyId().equals(family.getPropertyCompanyId())) {
        throw new BizException("不可加入跨物业的家庭");
    }

    // 合并积分到家庭池
    family.setPointBalance(family.getPointBalance() + r.getPointBalance());
    family.setCoinBalance(family.getCoinBalance().add(r.getCoinBalance()));
    family.setMemberCount(family.getMemberCount() + 1);
    familyRepository.save(family);

    r.setFamilyId(familyId);
    residentRepository.save(r);
}
```

#### 6.2.3 退出家庭

```java
public void leaveFamily(String residentId) {
    Resident r = residentRepository.findById(residentId);
    Family family = familyRepository.findById(r.getFamilyId());
    // 户主不可直接退出（需先转让户主或解散家庭）
    if (family.getOwnerId().equals(residentId)) {
        throw new BizException("户主不可直接退出，请先转让或解散家庭");
    }
    // 退出时按当前家庭人均积分分配
    int avgPoints = family.getPointBalance() / family.getMemberCount();
    BigDecimal avgCoin = family.getCoinBalance()
        .divide(BigDecimal.valueOf(family.getMemberCount()), 2, RoundingMode.DOWN);

    r.setPointBalance(avgPoints);
    r.setCoinBalance(avgCoin);
    r.setFamilyId(null);
    residentRepository.save(r);

    family.setPointBalance(family.getPointBalance() - avgPoints);
    family.setCoinBalance(family.getCoinBalance().subtract(avgCoin));
    family.setMemberCount(family.getMemberCount() - 1);
    familyRepository.save(family);
}
```

### 6.3 15 人上限校验

- 校验点：加入家庭时（`joinFamily` 方法）
- 上限值：15（硬编码，不可配置）
- 校验字段：`families.member_count`
- 并发场景：使用乐观锁或家庭维度的分布式锁（见第 14 章）

### 6.4 积分合并到家庭池的逻辑

```java
// 伪代码：用户获得积分时合并到家庭池
public void earnPoints(String residentId, int amount, String source) {
    Resident r = residentRepository.findById(residentId);
    r.setPointBalance(r.getPointBalance() + amount);
    residentRepository.save(r);

    if (r.getFamilyId() != null) {
        Family family = familyRepository.findByIdForUpdate(r.getFamilyId()); // 行锁
        family.setPointBalance(family.getPointBalance() + amount);
        familyRepository.save(family);
    }

    pointRecordsRepository.save(PointRecord.builder()
        .residentId(residentId)
        .familyId(r.getFamilyId())
        .pointType("earn")
        .amount(amount)
        .balance(r.getPointBalance())
        .source(source)
        .build());
}
```

> 个人积分与家庭池积分同时增加；消费时优先扣家庭池，扣完再扣个人。

### 6.5 一户一票投票权重

- `families.vote_weight` 恒为 1
- 投票时校验 `vote_records.family_id` 唯一性（`uk_opinion_family`）
- 同家庭任一成员投票即代表全家，其他成员再投拒绝

```java
public void vote(String residentId, String opinionBoxId, String option) {
    Resident r = residentRepository.findById(residentId);
    if (r.getFamilyId() == null) {
        throw new BizException("未加入家庭，无法投票");
    }

        .residentId(residentId)
        .familyId(r.getFamilyId())
        .voteOption(option)   // support/oppose/abstain
        .build());
}
```

### 6.6 家庭审核流程

- 创建家庭后 `audit_status='pending'`
- 物业审核通过后 `audit_status='approved'`，家庭功能正式生效
- 审核拒绝 `audit_status='rejected'`，家庭解散，成员退出
- 审核期间成员可加入但不可消费家庭池积分

### 6.7 异常处理

| 场景 | 处理 |
|------|------|
| 家庭人数超 15 | 拒绝加入，错误码 `FAMILY_MEMBER_LIMIT_EXCEEDED` |
| 跨物业加入 | 拒绝，错误码 `FAMILY_CROSS_PROPERTY_DENIED` |
| 户主直接退出 | 拒绝，提示先转让或解散 |
| 解散家庭 | 退还各成员按人均分配的积分/物业币，记录操作日志 |

## 7. 平台级商家库

### 7.1 规则描述

商家基础信息一次录入到平台级商家库 `platform_merchants`，各物业公司通过 `merchants` 表挂接并独立设定参数。

### 7.2 平台商家 vs 物业挂接商家的关系

```
platform_merchants（平台级，1 条）
    ├── merchants（物业 A 挂接，1 条）
    │     └── merchant_property_configs（物业 A 参数）
    ├── merchants（物业 B 挂接，1 条）
    │     └── merchant_property_configs（物业 B 参数）
    └── merchants（物业 C 挂接，1 条）
          └── merchant_property_configs（物业 C 参数）
```

- 平台商家记录基础信息：名称、描述、封面、分类、营业时间
- 物业挂接记录：商家在物业下的展示信息、审核状态、配送费、排序
- 参数配置记录：抽佣比例、积分兑换比、业主折扣价、物业币返现比

### 7.3 挂接流程

```java
// 伪代码：物业挂接平台商家
public Merchant linkMerchant(String platformMerchantId, String propertyId, LinkForm form) {
    // 1. 校验平台商家存在
    PlatformMerchant pm = platformMerchantRepository.findById(platformMerchantId);

        .platformMerchantId(platformMerchantId)
        .propertyCompanyId(propertyId)
        .name(form.getName() != null ? form.getName() : pm.getName())
        .merchantLevel("normal")
        .auditStatus("pending_audit")
        .deliveryFee(form.getDeliveryFee())
        .freeDeliveryThreshold(form.getFreeDeliveryThreshold())
        .build();
    merchant = merchantRepository.save(merchant);

    // 4. 创建参数配置
    merchantPropertyConfigsRepository.save(MerchantPropertyConfig.builder()
        .merchantId(merchant.getId())
        .propertyCompanyId(propertyId)
        .commissionRate(form.getCommissionRate())
        .pointExchangeRate(form.getPointExchangeRate())

```

### 7.4 参数独立配置

同一平台商家在不同物业下的参数完全独立，由 `merchant_property_configs` 表承载：

| 参数 | 物业 A | 物业 B |
|------|--------|--------|
| `commission_rate` | 0.10 | 0.15 |
| `point_exchange_rate` | 200 | 150 |
| `member_discount_price` | 8.5 折 | 9 折 |
| `coin_rebate_rate` | 0.05（启用） | 0.00（禁用） |

唯一索引 `uk_merchant_property (merchant_id, property_company_id)` 保证一个挂接仅一份配置。

### 7.5 商家分级

`merchants.merchant_level` 三级：

| 等级 | 含义 | `level_weight` |
|------|------|----------------|
| `official_certified` | 官方认证商家 | 最高（如 100） |
| `property_certified` | 物业认证商家 | 中（如 50） |
| `normal` | 普通商家 | 0 |

- 排序规则：`level_weight DESC, rank_order ASC`（高级别优先，同级别按手动拖拽）
- 升级需物业审核，记 `operation_logs`

### 7.6 异常处理

| 场景 | 处理 |
|------|------|
| 平台商家不存在 | 拒绝挂接 |
| 重复挂接 | 唯一索引拦截，提示"已挂接" |
| 参数缺失 | 挂接时强制要求 `commission_rate`、`point_exchange_rate` |
| 解除挂接 | 软删除 `merchants.status='inactive'`，保留历史订单数据 |

### 8.3 清零入池的执行流程

```java
// 伪代码：清零入池
@Transactional
public void executeClear(String residentId, String operatorId) {
    Resident r = residentRepository.findById(residentId);
    int clearedPoints = r.getPointBalance();
    if (clearedPoints <= 0) return;

    PropertyCompany pc = propertyCompanyRepository.findById(r.getPropertyCompanyId());
    BigDecimal poolInAmount = BigDecimal.valueOf(clearedPoints)
        .multiply(pc.getPointToFeeRate());   // 100 积分 × 0.01 = 1 元

    // 1. 扣减住户积分
    r.setPointBalance(0);
    residentRepository.save(r);

    // 2. 记录积分扣减
    pointRecordsRepository.save(PointRecord.builder()
        .residentId(residentId)
        .pointType("expire")
        .amount(-clearedPoints)
        .balance(0)
        .source("fee_clear")
        .description("2年欠费清零")
        .operatorId(operatorId)
        .build());

    // 3. 入积分池
    pointPoolService.poolIn(r.getPropertyCompanyId(), poolInAmount,
        "fee_clear", residentId);

    // 4. 记录操作日志
    operationLogsRepository.save(OperationLog.builder()
        .operatorId(operatorId)
        .module("point")
        .action("two_year_clear")
        .targetType("resident")
        .targetId(residentId)
        .afterData(JsonUtil.toJson(Map.of("clearedPoints", clearedPoints,
            "poolInAmount", poolInAmount)))
        .build());
}
```

## 9. 配送费统一规则

### 9.1 规则描述

配送费按物业公司维度统一配置起步价，快递员每单报酬固定。商家可在 `merchants.delivery_fee` 自行设定按单收费，在 `merchants.free_delivery_threshold` 设定满额免配送费。

### 9.2 配送费计算公式

```
基础配送费 base_fee = delivery_rules.base_fee              // 物业配置起步价
商家配送费 merchant_fee = merchants.delivery_fee           // 商家设定
满额免配送阈值 free_threshold = merchants.free_delivery_threshold

if (订单金额 ≥ free_threshold) {
    final_fee = 0
} else if (merchant_fee > 0) {
    final_fee = merchant_fee
} else {
    final_fee = base_fee
}

快递员报酬 courier_earning = delivery_rules.courier_per_order   // 固定每单（如 0.35 元）
```

### 9.3 快递员抢单机制

```java
// 伪代码：快递员抢单
public void grabOrder(String courierId, String orderId) {
    // 权限校验：快递员需有 delivery.grab 权限
    permissionService.check(courierId, "delivery.grab");

    Delivery delivery = deliveryRepository.findByOrderId(orderId);
    if (!"pending".equals(delivery.getStatus())) {
        throw new BizException("订单已被抢或不可抢");
    }
    // 分布式锁防止并发抢单
    String lockKey = "delivery:grab:" + orderId;
    if (!redisLock.tryLock(lockKey, courierId, 10)) {
        throw new BizException("抢单失败，请重试");
    }
    try {
        delivery.setCourierId(courierId);
        delivery.setStatus("accepted");
        delivery.setAcceptedAt(LocalDateTime.now());
        delivery.setCourierEarning(deliveryRulesRepository
            .findByPropertyCompanyId(delivery.getPropertyCompanyId())
            .getCourierPerOrder());
        deliveryRepository.save(delivery);
    } finally {
        redisLock.unlock(lockKey, courierId);
    }
}
```

### 9.4 物业兜底逻辑

- 订单发布后 `delivery_rules.timeout_minutes`（默认 30 分钟）内无人抢单
- 系统将 `deliveries.status` 改为 `property_fallback`
- `deliveries.courier_id` 置 null
- 物业承担配送任务，配送费归物业

```java
// 伪代码：物业兜底
@Scheduled(fixedDelay = 60000)

        .minusMinutes(30));
    for (Delivery d : timeouts) {
        d.setStatus("property_fallback");
        d.setCourierId(null);
        deliveryRepository.save(d);
        // 通知物业
        messageService.notifyProperty(d.getPropertyCompanyId(), "配送超时需兜底", d.getOrderId());
    }
}
```

### 9.5 满额免配送费

## 12. 权限体系规则

### 12.1 规则描述

权限体系采用三层模型：
1. **权限池**（`permissions`）：所有可用权限定义
2. **角色预设**（`role_presets` + `role_preset_permissions`）：快捷权限包
3. **用户权限覆盖**（`user_permissions`）：在预设基础上增减单项

### 12.2 三层模型

```
权限池 permissions
    ↓ 关联
角色预设 role_presets ←→ role_preset_permissions
    ↓ 加载到用户
用户基础权限 = 预设权限集合
    ↓ 覆盖
用户权限覆盖 user_permissions
    ↓ 最终
用户最终权限 = 基础权限 ∪ {granted=true} − {granted=false}
```

### 12.3 权限变更日志强制记录

任何权限变更（授予、撤销、应用预设）必须写入 `permission_change_logs`：

```java
// 伪代码：授予权限
@Transactional
public void grantPermission(String residentId, String permissionCode,
                           String operatorId, String propertyId) {
    Permission perm = permissionsRepository.findByCode(permissionCode);
    UserPermission exist = userPermissionsRepository
        .findByResidentIdAndPermissionId(residentId, perm.getId());

    String beforeValue = exist == null ? "null" : String.valueOf(exist.isGranted());
    if (exist == null) {
        userPermissionsRepository.save(UserPermission.builder()
            .residentId(residentId)
            .permissionId(perm.getId())
            .granted(true)
            .propertyCompanyId(propertyId)
            .operatorId(operatorId)
            .build());
    } else {
        exist.setGranted(true);
        userPermissionsRepository.save(exist);
    }

    // 强制记录日志
    permissionChangeLogsRepository.save(PermissionChangeLog.builder()
        .residentId(residentId)
        .operatorId(operatorId)
        .propertyCompanyId(propertyId)
        .action("grant")
        .permissionCode(permissionCode)
        .beforeValue(beforeValue)
        .afterValue("true")
        .build());
}
```

- 不记录日志的权限变更视为非法操作
- 日志保留期 ≥ 2 年，仅供审计

### 12.4 权限校验流程

```java
// 伪代码：权限校验
public boolean hasPermission(String residentId, String permissionCode) {
    Resident r = residentRepository.findById(residentId);
    if ("platform_admin".equals(r.getRole())) return true;

    Permission perm = permissionsRepository.findByCode(permissionCode);
    if (perm == null) return false;

    // 1. 查用户覆盖表
    UserPermission override = userPermissionsRepository
        .findByResidentIdAndPermissionId(residentId, perm.getId());
    if (override != null) {
        return override.isGranted();
    }

    // 2. 未覆盖则查角色预设
    List<RolePreset> presets = rolePresetRepository.findByResidentRole(r.getRole());
    for (RolePreset preset : presets) {
        if (rolePresetPermissionsRepository
            .existsByPresetIdAndPermissionId(preset.getId(), perm.getId())) {
            return true;
        }
    }
    return false;
}
```

### 12.5 数据表字段映射

| 字段 | 表 | 含义 |
|------|----|------|
| `code` | `permissions` | 权限编码（如 `announcement.publish`） |
| `code` | `role_presets` | 预设编码（如 `coordinator`） |
| `granted` | `user_permissions` | TRUE=勾选/FALSE=取消覆盖 |
| `action` | `permission_change_logs` | grant/revoke/apply_preset |
| `before_value`、`after_value` | `permission_change_logs` | 变更前后值 |

## 14. 并发与一致性

### 14.1 订单支付的乐观锁

`orders` 表含 `version INT DEFAULT 0` 字段，更新时使用 JPA `@Version`：

```java
@Entity

    @Version
    private Integer version;
}

// 支付时乐观锁更新
@Transactional
public void payOrder(String orderId, PaymentForm form) {
    Order order = orderRepository.findById(orderId).orElseThrow();
    order.setOrderStatus("paid");
    order.setPaymentMethod(form.getMethod());
    order.setPaidAt(LocalDateTime.now());
```

- 并发更新失败时重试 3 次
- 重试仍失败提示"订单状态已变更，请刷新"

### 14.2 积分扣减的原子性

```java
// 伪代码：积分扣减原子操作
@Transactional
public void deductPoints(String residentId, int amount, String source) {
    Resident r = residentRepository.findByIdForUpdate(residentId);  // SELECT ... FOR UPDATE
    if (r.getPointBalance() < amount) {
        throw new BizException("积分不足");
    }
    r.setPointBalance(r.getPointBalance() - amount);
    residentRepository.save(r);

    pointRecordsRepository.save(PointRecord.builder()
        .residentId(residentId)
        .pointType("spend")
        .amount(-amount)
        .balance(r.getPointBalance())
        .source(source)
        .build());

    // 同步扣家庭池
    if (r.getFamilyId() != null) {
        Family f = familyRepository.findByIdForUpdate(r.getFamilyId());
        f.setPointBalance(f.getPointBalance() - amount);
        familyRepository.save(f);
    }
}
```

- 使用行锁 `SELECT ... FOR UPDATE` 保证扣减原子性
- 个人与家庭池同步扣减，任一失败则整体回滚（`@Transactional`）

### 14.3 物业币扣减的原子性

与积分扣减类似，使用行锁：

```java
@Transactional
public void deductCoin(String residentId, BigDecimal amount, String source) {
    Resident r = residentRepository.findByIdForUpdate(residentId);
    if (r.isCoinFrozen()) {
        throw new BizException("物业币已冻结");
    }
    if (r.getCoinBalance().compareTo(amount) < 0) {
        throw new BizException("物业币不足");
    }
    r.setCoinBalance(r.getCoinBalance().subtract(amount));
    residentRepository.save(r);

    propertyCoinRecordsRepository.save(PropertyCoinRecord.builder()
        .residentId(residentId)
        .coinType("spend")
        .amount(amount.negate())
        .balance(r.getCoinBalance())
        .source(source)
        .build());

    if (r.getFamilyId() != null) {
        Family f = familyRepository.findByIdForUpdate(r.getFamilyId());
        f.setCoinBalance(f.getCoinBalance().subtract(amount));
        familyRepository.save(f);
    }
}
```

- 冻结状态校验优先于余额校验
- 家庭池同步扣减

### 14.4 分布式锁使用场景

| 场景 | 锁键 | 持有方 | 用途 |
|------|------|--------|------|
| 快递员抢单 | `delivery:grab:{orderId}` | 快递员 ID | 防止并发抢单 |
| 家庭成员加入 | `family:join:{familyId}` | 住户 ID | 防止 15 人上限并发突破 |
| 投票 | `vote:{opinionBoxId}:{familyId}` | 投票成员 ID | 防止一户多票 |
| 商家提现 | `withdraw:{merchantId}` | 商家 ID | 防止余额并发超扣 |
| 积分池操作 | `pool:{propertyId}` | 任务 ID | 防止池余额并发更新 |

```java
// 伪代码：分布式锁模板
public <T> T executeWithLock(String lockKey, String owner, long expireSeconds,
                             Supplier<T> action) {
    boolean locked = redisLock.tryLock(lockKey, owner, expireSeconds);
    if (!locked) {
        throw new BizException("操作并发，请稍后重试");
    }
    try {
        return action.get();
    } finally {
        redisLock.unlock(lockKey, owner);
    }
}
```

### 14.5 一致性保障原则

1. **订单 + 分成 + 积分入账** 三步必须同事务（`@Transactional`），任一失败整体回滚
2. **积分池入池** 允许异步处理（消息队列），但需保证最终一致性
3. **物业币过期清零** 通过定时任务批量处理，单住户单事务
4. **家庭池更新** 与个人账户更新同事务，使用行锁
5. **跨服务调用**（如配送通知）采用最终一致性，本地事务+消息队列

### 14.6 异常处理

| 场景 | 处理 |
|------|------|
| 乐观锁冲突 | 重试 3 次，仍失败提示刷新 |
| 行锁等待超时 | 503 服务繁忙，请稍后重试 |
| 分布式锁获取失败 | 提示"操作并发，请稍后重试" |
| 事务部分失败 | 整体回滚，不留中间状态 |
