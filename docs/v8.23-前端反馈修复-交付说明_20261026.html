01商家余额口径 口径确认

反馈 2.1：同一个住户既是商家又是楼长时，商家页的「盈利余额」会不会把楼长分成、业主卖货收益算进去？

结论

不会。profitBalance 是本商家店铺口径，只包含本店订单收益，不含楼长分成、业主卖货收益。

withdrawableAmount 是本店提现入口实际可用：商家提现同时校验「本店铺可提现」和「账号统一可提现」，因此它等于 min(shopWithdrawableAmount, accountWithdrawableAmount)。此前文档 §5 的 withdrawableAmount 指的是楼长工作台的「账号统一可提现」，不是商家接口。为避免再混淆，v8.23 新增了显式字段。

字段

字段口径说明
withdrawableAmount本店提现入口实际可用 = min(shopWithdrawableAmount, accountWithdrawableAmount)；商家提现页用这个
shopWithdrawableAmount本店铺本店可提现（店铺收益 − 店铺提现占用），未受其他角色占用影响
profitBalance本店铺盈利余额（店铺口径，与 shopWithdrawableAmount 同值）
profitScope—固定 shop，前端据此判断文案
accountWithdrawableAmount账号统一楼长分成 + 业主卖货收益 + 名下商家剩余可提现，扣全部角色提现在途
正常情况 accountWithdrawableAmount >= shopWithdrawableAmount，此时 withdrawableAmount = shopWithdrawableAmount。 若同一住户已通过楼长/卖货入口提走了部分款项，账号统一余额可能低于店铺余额，withdrawableAmount 会取更小的账号值，避免超额提现。 商家提现接口仍只允许本店提现入口；楼长/卖货部分请走各自角色的提现入口。

响应示例

{
  "code": 0,
  "data": {
    "id": "mch_xxx",
    "name": "幸福超市",
    "withdrawableAmount": 1280.50,
    "shopWithdrawableAmount": 1280.50,
    "profitBalance": 1280.50,
    "profitScope": "shop",
    "accountWithdrawableAmount": 1580.50,
    "totalOrders": 128,
    "pointBalance": 5000
  }
}

前端文案建议：profitBalance / shopWithdrawableAmount → 「本店可提现 / 本店盈利余额」；提现页可用金额 → withdrawableAmount；需要展示「账号可提现」时，读 accountWithdrawableAmount，不要用 profitBalance。

02广告补付与重复提交 新增接口

反馈 2.2：已存在的待支付广告如何补付？重复提交 POST /merchant/ads 会不会生成两条广告？

新增补付接口

POST /merchant/ads/{id}/repay（需登录，角色 merchant，仅广告所属商家）

场景结果
待支付 / 支付超时取消的微信现金广告200 + 新的 payParams
已支付/已投放409（70003）广告已投放，无需重复支付
免费额度或非微信广告400（10002）该广告无需支付
微信支付未开启400（10002）广告微信支付暂未开放
操作其他商家的广告403（20004）
 
POST /api/v1/merchant/ads/mad_xxx/repay
Authorization: Bearer <token>

{
  "code": 0,
  "data": {
    "id": "mad_xxx",
    "status": "pending_payment",
    "payStatus": "unpaid",
    "payAmount": 70.00,
    "canRepay": true,
    "paymentRecordId": "pr_xxx",
    "payParams": {
      "timeStamp": "1730000000",
      "nonceStr": "abc123",
      "package": "prepay_id=wx123",
      "signType": "RSA",
      "paySign": "xxxx"
    }
  }
}

前端流程：列表项 canRepay=true → 调 repay → 拿 payParams 调 wx.requestPayment → 支付回调后后端置 active，刷新列表。

列表新增字段

字段类型说明
paymentRecordIdstring最近一笔支付流水 ID（含待支付/已关闭流水），补付或查单用
canRepayboolean是否可继续支付
remainingDaysnumber剩余投放天数；未支付或已结束为 0
补付接口内置行锁与流水复用：5 分钟内重复点击复用同一笔待支付流水，不会重复扣款；超过 5 分钟的旧流水关闭后重新预下单。

重复提交

  • POST /merchant/ads / POST /merchant/ads/targeted 每次成功调用都会创建一条新广告；
  • 前端可带请求头 X-Request-Id（8–128 位字母/数字/._:-）做幂等：同一用户 + 同一路径 + 同一 ID 会回放首次成功响应，不会重复建广告；
  • 已存在的待支付广告请走 repay，不要重新发布。

反馈 2.3：居民端从哪里读 point_transfer_enabled / point_transfer_min_years？是否还要返回入住年限是否满足？

04广告状态全量枚举 枚举补齐

反馈 2.4：status / payStatus 的完整取值是什么？「投放中」和「已结束」以哪个字段为准？

status（列表展示状态）

值含义说明
pending_payment待支付微信现金广告已下单、未收款
active投放中已支付/免费投放，且 endDate >= 今天
ended已结束派生值：数据库仍为 active，endDate < 今天 时返回 ended
cancelled已取消支付超时/失败，由后端定时任务置为取消

当前系统没有 expired / rejected / paused 状态。

payStatus（支付状态）

值含义说明
unpaid未支付无已支付流水
paid已支付含免费额度投放
refunded已退款预留值；当前广告无退款流程，暂不会产生
「投放中 / 已结束」以 status 为准，不要用 payStatus 判断。 canRepay=true 仅出现在 status=pending_payment 或 cancelled、支付方式为 wechat 且尚未支付的广告。

06商品/店铺字段与跳转 字段补齐

反馈 2.6：shopId 是商家 ID 还是业主小店 ID？应该往哪套详情页跳？

结论

shopId 明确为 merchants.id（不是业主小店上架 ID）。GET /products 与 GET /products/{id} 新增以下字段：

字段类型说明
shopIdstringmerchants.id

07货源供给范围权限 权限明确

反馈 2.7：supply_scope=platform 由谁设置？代理能不能自己改？

结论

只有平台管理员 / 物业管理员能设置；一级代理只能只读展示。当前系统没有单独的「超级代理」角色，platform 是按商品授予的供给范围。

入口行为
POST /admin/distributor-products管理端可传 supplyScope（默认 company）
PUT /admin/distributor-products/{id}管理端可改 supplyScope 为 company/platform
GET /distributors/my/products返回 supplyScope 只读
GET /distributors/products返回 supplyScope 只读
POST/PUT /distributors/my/products不要传 supplyScope；传任意非空值（含 company）返回 403（20004）

物业管理员只能操作本物业公司的货源，跨物业返回 403。代理新建货源时后端固定写 company，不会因为漏传而变成 platform。

PUT /api/v1/admin/distributor-products/dpr_xxx
Authorization: Bearer <property_admin_token>
Content-Type: application/json

{ "supplyScope": "platform" }
前端代理端编辑弹窗保持只读展示即可；当前实现（不回传）是正确的。

09家庭转账历史流水 口径确认

反馈 2.9：家庭转账下线后，历史流水的 source 保留原值还是统一改名？前端「转账」筛选还能命中吗？

结论

  • 历史家庭内转赠流水保留原值：pointType=transfer、source=transfer，不做数据改写；
  • transfer_to_property（积分转物业）是另一用途，保持独立；用 source=transfer 筛选不会混入转物业流水；
  • GET /points/records?source=transfer 会同时命中历史 transfer 与早期 family_transfer 两种取值；
  • 前端传 source=family_transfer 也会被后端归一为 transfer 查询，同样命中；
  • 新增流水不再产生家庭转赠（入口已下线），因此「转账」筛选只会命中历史数据。
前端「转账」筛选继续传 source=transfer 即可，无需特殊处理历史数据。
