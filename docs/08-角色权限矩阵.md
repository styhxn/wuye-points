# 角色权限矩阵 - 物业积分服务系统

> 适用版本：PRD V4.1
> 配套文档：`02-数据库设计.md`（§13 权限体系模块）、`03-API接口设计.md`、`09-Web后台API设计.md`

## 1. 概览

### 1.1 权限体系三层模型

系统采用 **"权限池 → 角色预设 → 用户覆盖"** 三层模型，所有变更强制落库审计：

| 层级 | 数据表 | 作用 | 说明 |
|------|--------|------|------|
| ① 权限池 | `permissions` | 20 个原子权限项 | 全平台统一的权限定义源，按 `module` 分组，`code` 唯一 |
| ② 角色快捷预设 | `role_presets` + `role_preset_permissions` | 6 个角色预设 | 将权限项打包成"快捷模板"，新建账号时一键应用 |
| ③ 用户权限覆盖 | `user_permissions` | 针对单用户的增/减 | `granted=TRUE` 为额外授权，`granted=FALSE` 为收回（覆盖预设） |
| ④ 变更日志 | `permission_change_logs` | 全量审计 | grant / revoke / apply_preset 三类动作强制记录 |

### 1.2 权限生效优先级

```
最终权限 = ( 角色预设权限 ∪ 用户授权项 ) − 用户收回项
```

- **用户级 > 预设级**：`user_permissions` 中的 `granted=FALSE` 可收回预设中已赋予的权限
- 同一 `(resident_id, permission_id)` 在 `user_permissions` 中唯一（`uk_resident_permission`），后写覆盖先写
- `residents.role` 决定默认预设；`user_permissions` 决定个性化偏差

### 1.3 与数据隔离的关系

权限矩阵回答 **"能不能做"**，数据隔离回答 **"能对谁的数据做"**。即使拥有某权限，`property_admin` 仍只能操作本公司 `property_company_id` 范围内的数据（见 §9）。

## 2. 角色清单（8 种角色）

| # | 角色 code | 名称 | 职责 | 数据范围 | 默认预设 |
|---|-----------|------|------|----------|----------|
| 1 | `platform_admin` | 平台管理员 | 跨物业公司最高权限，负责物业公司入驻/停用、平台级商家库、全局配置 | 全平台所有物业公司 | `PLATFORM_ADMIN_PRESET` |
| 2 | `property_admin` | 物业管理员 | 单物业公司内最高权限，负责本公司商家审核、用户管理、分成、物业费、物业币、报表 | 仅本人所属 `property_company_id` | `PROPERTY_ADMIN_PRESET` |

| 4 | `sector_leader` | 板块负责人 | 管理个体负责人，从统筹抽 10%，按 `sector`（elderly/medical/education/...）划分 | 本公司内其负责的板块 | `SECTOR_LEADER_PRESET` |
| 5 | `individual_leader` | 个体负责人 | 管理特定商家/服务（如钢琴老师），从板块抽成 | 本人负责的个体范围 | 继承 `SECTOR_LEADER_PRESET` + 用户覆盖 |

## 5. 用户权限覆盖（user_permissions）

> 对应 `user_permissions` 表：`resident_id` / `permission_id` / `granted` / `property_company_id` / `operator_id`，唯一键 `uk_resident_permission(resident_id, permission_id)`。

### 5.1 授权（grant）流程

1. `property_admin` / `platform_admin` 在后台账号权限页勾选某权限项
2. 调用 `PUT /api/v1/admin/accounts/:id/permissions`，传入 `addPermissionCodes`
3. 服务端 upsert `user_permissions`（`granted=TRUE`）
4. 写入 `permission_change_logs`（`action=grant`，记录 `before_value`/`after_value`）
5. 用户下次请求时权限即时生效（权限缓存可在 5 分钟内刷新或主动失效）

### 5.2 收回（revoke）流程

1. 勾除某权限项，传入 `removePermissionCodes`
2. 服务端 upsert `user_permissions`（`granted=FALSE`）—— **覆盖预设**
3. 写入 `permission_change_logs`（`action=revoke`）
4. 即时失效用户该权限

### 5.3 覆盖优先级

- **用户级 > 预设级**：`granted=FALSE` 可让预设中已含的权限对该用户失效
- `apply-preset` 接口（`POST /accounts/:id/apply-preset`）默认清空 `user_permissions`（`keepCustomPermissions=false`）；若传 `true` 则保留自定义覆盖
- `resetCustom=true` 可一键清除某用户全部自定义覆盖，回归纯预设状态

### 5.4 操作示例

```jsonc
// 给 courier 用户 res_001 授予抢单权限
PUT /api/v1/admin/accounts/res_001/permissions
{
  "addPermissionCodes": ["delivery:grab"]
}

// 给某 coordinator 收回 merchant:audit 权限
PUT /api/v1/admin/accounts/res_002/permissions
{
  "removePermissionCodes": ["merchant:audit"]
}

// 给某用户应用统筹预设并保留原有自定义权限
POST /api/v1/admin/accounts/res_003/apply-preset
{
  "presetId": "rp_coord_001",
  "keepCustomPermissions": true
}
```

## 6. 权限变更日志（permission_change_logs）

> 对应 `permission_change_logs` 表：`resident_id` / `operator_id` / `property_company_id` / `action` / `permission_code` / `preset_code` / `before_value` / `after_value`。

### 6.1 强制记录规则

- **所有**权限相关写操作必须落库日志，无例外
- 涉及动作：`grant`（授权单项）、`revoke`（收回单项）、`apply_preset`（应用预设）
- 日志与业务操作在同一事务内提交，保证一致性
- 日志不可修改、不可删除（仅追加）

### 6.2 日志字段说明

| 字段 | 说明 | 示例 |
|------|------|------|
| `resident_id` | 被操作用户 ID | `res_001` |
| `operator_id` | 操作人 ID | `res_admin001` |
| `property_company_id` | 所属物业公司 | `pc_a1b2c3d4` |
| `action` | 动作类型 | `grant` / `revoke` / `apply_preset` |
| `permission_code` | 涉及的权限码（apply_preset 时可空） | `delivery:grab` |
| `preset_code` | 涉及的预设码（grant/revoke 时可空） | `COORDINATOR_PRESET` |
| `before_value` | 变更前状态 | `granted=FALSE` |
| `after_value` | 变更后状态 | `granted=TRUE` |
| `created_at` | 操作时间 | `2026-07-01T10:00:00.000Z` |

### 6.3 审计场景

- **合规追溯**：通过 `GET /api/v1/admin/permission-logs?accountId=xxx` 查询某用户全部权限变更历史
- **操作复盘**：按 `operatorId` 筛选，定位某管理员的所有授权操作
- **异常检测**：批量 grant/revoke、离职前的权限清理、跨物业越权尝试
- **离职处理**：员工离职时一键 `status=disabled`，日志记录"账号禁用"事件，保留历史权限快照

## 7. 权限校验流程

### 7.1 校验链路

```
接口请求
  ↓
① JWT 解析 → 取出 resident_id、role、property_company_id
  ↓
② 角色匹配 → 校验 role 是否在接口允许角色列表内（不匹配 → 403/10004）
  ↓
③ 数据隔离校验 → property_admin 路径 :id 是否等于其 property_company_id（不符 → 403/20003）
  ↓
④ 权限池校验 → 加载用户最终权限集（预设 ∪ grant − revoke）
  ↓
⑤ 用户覆盖合并 → 命中所需 permission_code？（未命中 → 403/10004）
  ↓
⑥ 放行 / 拒绝
```

### 7.2 伪代码实现

```typescript
// 中间件：requirePermission('merchant:audit', ['platform_admin','property_admin'])
async function checkPermission(req, requiredPermCode, allowedRoles) {
  // ① JWT 已由前置中间件解析为 req.user
  const { residentId, role, propertyCompanyId } = req.user;

  // ② 角色匹配
  if (!allowedRoles.includes(role)) {
    throw new BizError(10004, '权限不足：角色不允许');
  }

  // ③ 数据隔离（property_admin 只能操作本公司）
  if (role === 'property_admin') {
    const targetPcId = req.params.propertyCompanyId || req.query.propertyCompanyId;
    if (targetPcId && targetPcId !== propertyCompanyId) {
      throw new BizError(20003, '跨物业公司访问被拒');
    }
  }

  // ④ 加载最终权限集（带缓存，5 分钟 TTL）
  const perms = await loadEffectivePermissions(residentId);
  // loadEffectivePermissions:
  //   1. 查 residents.role → 映射预设 code → 取 role_preset_permissions
  //   2. 查 user_permissions(resident_id) → granted=TRUE 并入，granted=FALSE 剔除

  // ⑤ 权限校验
  if (!perms.includes(requiredPermCode)) {
    throw new BizError(10004, '权限不足：缺少 ' + requiredPermCode);
  }

  // ⑥ 放行
  req.user.effectivePermissions = perms;
  next();
}
```

### 7.3 性能要点

- 用户最终权限集按 `resident_id` 缓存（Redis，TTL 5 分钟）
- 权限变更时主动删除该用户的缓存键，确保即时生效
- `permissions`、`role_presets`、`role_preset_permissions` 三表低频变更，可全量缓存

## 8. 接口-角色-权限映射总表

## 9. 数据隔离与角色关系

### 9.1 物业公司维度隔离

所有业务表均含 `property_company_id` 字段，Repository 层强制过滤（见 `02-数据库设计.md` §1）。

| 角色 | 数据范围 | 实现机制 |
|------|----------|----------|
| `platform_admin` | 全平台所有物业公司 | 可显式传 `propertyCompanyId` 指定目标公司；不传则汇总全平台 |
| `property_admin` | 仅本人所属 `property_company_id` | 服务端自动注入当前账号 `propertyCompanyId`，路径中 `:id` 必须等于其所属公司，否则 `403/20003 forbidden_company_access` |
| `coordinator` | 本公司内其负责的板块 | 通过 `coordinators` 表关联 `sector_leaders`，查询限定 `coordinator_id = 当前用户` |
| `sector_leader` | 本人负责的板块（`sector`）下 | 通过 `sector_leaders.id` 限定，个体负责人查询限定 `sector_leader_id = 当前用户` |
| `individual_leader` | 本人负责的个体 | 通过 `individual_leaders.id` 限定关联商家/服务 |
| `merchant` | 仅本人商家 `merchant_id` | 所有商品/订单/提现查询限定 `merchant_id = 当前商家` |
| `courier` | 所属物业公司范围内可抢订单 | 抢单列表限定 `property_company_id`，已接单限定 `courier_id = 当前用户` |
| `resident` | 仅本人及家庭 `family_id` | 所有积分/物业币/订单查询限定 `resident_id` 或 `family_id` |

### 9.2 角色层级与分成关系

```
platform_admin（跨物业）
  └─ property_admin（单物业）
       └─ coordinator（统筹，分成 70%）
            └─ sector_leader（板块负责人，从统筹抽 10%）
                 └─ individual_leader（个体负责人，从板块抽成）
       └─ merchant（商家，管理自己的商品/订单）
       └─ courier（快递员，抢单配送）
       └─ resident（业主/住户）
            └─ activity_leader（活动组组长，子角色）
```

- 分成比例配置于 `property_companies` 表：`property_share_rate`(30%) / `coordinator_share_rate`(70%) / `sector_leader_rate`(10%) / `individual_leader_rate`
- 分成记录落库 `distribution_records`，含 `coordinator_id` / `sector_leader_id` / `individual_leader_id`

### 9.3 数据隔离实现要点

1. 自定义注解 `@PropertyScope` 标记需数据隔离的接口
2. 拦截器统一注入当前账号 `propertyCompanyId` 到查询条件
3. `platform_admin` 通过 Query 参数 `propertyCompanyId` 显式指定
4. 所有 SQL 查询必须含 `property_company_id` 条件（平台级表除外：`platform_merchants` / `permissions` / `role_presets` 等）

## 10. 特殊场景

### 10.1 角色切换（一个用户多角色）

- `residents.role` 字段为单值，记录 **主角色**
- 当用户兼具多个身份时（如业主同时是个体负责人），通过 `user_permissions` 为其额外授予对应角色预设的权限子集
- 示例：业主 `res_001` 兼任快递员 → 主角色 `resident`，`user_permissions` 额外授予 `delivery:grab`
- 前端根据 `effectivePermissions` 动态展示功能入口

### 10.2 临时授权

- 场景：活动期间临时赋予某员工报表查看权限
- 操作：`PUT /accounts/:id/permissions` 授权 `report:view`，记录 `permission_change_logs`
- 到期处理：定时任务扫描临时授权记录，到期自动 `revoke` 并写日志；或人工 `removePermissionCodes`

### 10.3 角色降级/升级

| 场景 | 处理 |
|------|------|
| 升级（resident → individual_leader） | 更新 `residents.role`；应用 `SECTOR_LEADER_PRESET`；写入 `coordinators`/`sector_leaders`/`individual_leaders` 关联表 |
| 降级（coordinator → resident） | 更新 `residents.role`；应用 `RESIDENT_PRESET`（清空 `user_permissions`）；撤销 `coordinators` 表记录（`status=inactive`）；保留历史分成记录 |
| 跨物业调岗 | `POST /admin/residents/:id/migrate` 迁移至新物业公司，权限按新公司重新配置 |

### 10.4 离职处理

1. `PATCH /admin/residents/:id/status` 设为 `disabled`，账号立即无法登录
2. 该用户所有 JWT Token 立即失效（加入黑名单）
3. 若为统筹/板块/个体负责人：撤销任职记录（`status=inactive`），其下属临时挂接到上级或等待重新任命
4. 若为物业管理员：清理 `user_permissions`，保留 `permission_change_logs` 用于审计
5. 保留历史业务数据（订单、分成记录、积分记录）不删除，仅账号不可用
